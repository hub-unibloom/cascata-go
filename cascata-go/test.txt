# Relatório Completo do Sistema de Branches - Análise Exata do Código

Este relatório documenta EXATAMENTE como o sistema de branches funciona, baseado APENAS no código lido. Sem suposições ou certezas falsas.

## Resumo Executivo

O sistema atual NÃO implementa isolamento total entre branches. Quando um merge é realizado, ele afeta DIRETAMENTE o banco de destino (geralmente "main"), e outros branches que usam o mesmo banco podem ser afetados. O sistema usa uma arquitetura de "thin clone" para branches de ambiente, mas o merge aplica mudanças no banco compartilhado.

```go
func (s *BranchService) createDataBranchDB(ctx context.Context, dbName, projectSlug string) error {
    templateDB := fmt.Sprintf("cascata_%s", projectSlug)
    
    // Sanitização
    if !isValidDBName(dbName) {
        return fmt.Errorf("invalid database name")
    }
    
    sanitizedDBName := sanitizeIdentifier(dbName)
    sanitizedTemplateDB := sanitizeIdentifier(templateDB)
    
    query := fmt.Sprintf("CREATE DATABASE %s TEMPLATE %s", sanitizedDBName, sanitizedTemplateDB)
    
    _, err := s.pool.Exec(ctx, query)
    return err
}
```

**O que acontece**:
- Usa o banco do projeto como template: `cascata_{project_slug}`
- Cria novo banco: `cascata_{project_slug}_{branch_name}_data`
- Usa CREATE DATABASE ... TEMPLATE (cópia completa do banco)

```go
func (s *BranchService) materializeThinClone(ctx context.Context, branch *Branch, sourceDB, targetDB string) error
```

**Fluxo EXATO**:

##### Passo 4.1: Verifica se Banco Já Existe (linhas 927-978)
```go
var exists bool
checkSQL := `SELECT EXISTS(SELECT 1 FROM pg_database WHERE datname = $1)`
_ = s.pool.QueryRow(ctx, checkSQL, targetDB).Scan(&exists)

if !exists {
    createSQL := fmt.Sprintf("CREATE DATABASE %s", pgx.Identifier{targetDB}.Sanitize())
    if _, err := s.pool.Exec(ctx, createSQL); err != nil {
        return fmt.Errorf("failed to create database %s: %w", targetDB, err)
    }
} else {
    // Banco já existe - sequência de drop seguro
    log.Printf("[materializeThinClone] Collision detected for %s - initiating safe drop sequence", targetDB)
    
    // Passo 1: Fecha/invalida o pool do backend para este banco
    services.Reload(targetDB)
    time.Sleep(100 * time.Millisecond)
    
    // Passo 2: Termina TODAS as conexões ativas
    terminateSQL := fmt.Sprintf(
        "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = $1 AND pid <> pg_backend_pid()",
    )
    _, _ = s.pool.Exec(ctx, terminateSQL, targetDB)
    
    // Passo 3: DROP DATABASE WITH (FORCE)
    dropSQL := fmt.Sprintf("DROP DATABASE %s WITH (FORCE)", pgx.Identifier{targetDB}.Sanitize())
    _, err := s.pool.Exec(ctx, dropSQL)
    if err != nil {
        dropSQL = fmt.Sprintf("DROP DATABASE %s", pgx.Identifier{targetDB}.Sanitize())
        _, _ = s.pool.Exec(ctx, dropSQL)
    }
    
    // Passo 4: Recria o banco limpo
    createSQL := fmt.Sprintf("CREATE DATABASE %s", pgx.Identifier{targetDB}.Sanitize())
    if _, err := s.pool.Exec(ctx, createSQL); err != nil {
        return fmt.Errorf("failed to recreate database %s after collision: %w", targetDB, err)
    }
    
    log.Printf("[materializeThinClone] Safe drop/recreate completed for %s", targetDB)
}
```

**O que acontece**:
- Se banco não existe: CREATE DATABASE
- Se banco existe: fecha conexões, termina backends, DROP WITH FORCE, recria

## 6. PROBLEMA CRÍTICO IDENTIFICADO

### 6.1 Onde os Branches se Misturam

**Localização**: `backend/internal/domain/branching/deployer/deployer.go:438-444` e `backend/internal/domain/branching/deployer/transaction.go:89-93`

```go
// No DeployMerge
result, err := c.Deployer.DeployMerge(
    r.Context(),
    ctx.Project.Slug,
    req.SourceBranch,  // ex: "feat/novo-checkout"
    req.TargetBranch,  // ex: "main"
    opts,
)

// No ExecuteDeploy
conn, err := d.poolProvider.AcquireForProject(projectSlug, env)  // env = targetBranch = "main"
```

**O que acontece**:
1. Quando você faz merge de "feat/novo-checkout" → "main"
2. O diff engine gera SQL comparando os dois bancos
3. O ExecuteDeploy aplica esse SQL DIRETAMENTE no banco "main"
4. Isso modifica o banco de produção
5. Outros branches que usam o mesmo banco "main" são afetados

### 6.2 Por Que Isso Acontece

**Localização**: `backend/internal/services/project.go:184-197`

```go
// ISOLATION GUARD: Se não for o ambiente 'live', resolvemos o banco da branch
if env != "" && env != "live" && project.Metadata.ExternalDbUrl == "" {
    var materializedDB string
    err := SystemPool.QueryRow(context.Background(),
        "SELECT materialized_db FROM system.branches WHERE project_slug = $1 AND name = $2 AND status = 'active'",
        project.Slug, env).Scan(&materializedDB)
    
    if err == nil && materializedDB != "" {
        dbName = materializedDB
    } else {
        log.Printf("[ProjectPool:Warn] Branch %s not materialized for project %s. Falling back to Live (UNSAFE).", env, project.Slug)
    }
}
```

**Problema**:
- Se env = "main", NÃO há redirecionamento
- Usa dbName = project.DbName (banco de produção)
- Quando merge é feito para "main", modifica o banco compartilhado

### 6.3 Como Deveria Ser (Multi-Tenancy Real)

Para isolamento total, cada branch deveria:
1. Ter seu próprio banco PostgreSQL (já implementado para data branches)
2. O merge deveria:
   - Comparar branch → main
   - Gerar SQL
   - Aplicar SQL apenas no banco da branch de destino
   - NUNCA tocar no banco de outras branches

**O que está faltando**:
- Environment branches não têm bancos próprios na criação
- Materialização é on-demand e usa thin clone
- Merge para "main" afeta o banco compartilhado
- Não há isolamento real entre branches

## 7. Resumo das Variáveis de Conexão

### 7.1 Variável `env`

**Onde é usada**: `GetProjectPool(project, env)`

**Valores possíveis**:
- `"live"` → banco de produção `cascata_{project_slug}`
- `"main"` → banco de produção `cascata_{project_slug}` (mesmo que live)
- `"feat/novo-checkout"` → banco materializado `cascata_{project_slug}_feat_novo-checkout_env`
- Nome de qualquer branch → banco materializado dessa branch

**Como é determinada**:
1. Via header `X-Cascata-Env` (set pelo middleware branch_rewriter.go)
2. Via cookie `cascata_active_env` (set pelo AccessBranch)
3. Via parâmetro em DeployBranch (targetBranch)

### 7.2 Variável `materialized_db`

**Onde é usada**: Campo em `system.branches`

**Quando é preenchida**:
- NULL quando branch é criada (apenas metadados)
- Preenchida com nome do banco quando AccessBranch é chamado
- Exemplo: `"cascata_meu-projeto_feat_novo-checkout_env"`

**Como é usada**:
- GetProjectPool consulta esse campo
- Se existe, redireciona para esse banco
- Se não existe, fallback para live (UNSAFE)

## 9. Conclusão

### 9.1 Estado Atual

**O que funciona**:
- Criação de branches com metadados
- Materialização on-demand de environment branches (thin clone)
- Criação de bancos dedicados para data branches
- Diff engine completo (7 fases)
- Histórico de deploys

**O que NÃO funciona (isolamento)**:
- Merge para "main" modifica o banco de produção compartilhado
- Outros branches podem ser afetados por mudanças no main
- Environment branches não têm isolamento real
- Fallback para live quando branch não materializada (UNSAFE)

### 9.2 Por Que Merge Afeta Outros Branches

**Causa raiz**: O sistema usa um banco compartilhado para "main" e branches não materializados. Quando merge é feito para "main", o SQL é aplicado diretamente nesse banco compartilhado.

**Fluxo do problema**:
1. Branch A é criada (apenas metadados, sem banco)
2. Branch B é criada (apenas metadados, sem banco)
3. Merge A → main aplica SQL no banco de produção
4. Branch B, quando acessada, pode ver as mudanças do merge
5. Não há isolamento entre branches

### 9.3 Solução Necessária

Para isolamento total (multi-tenancy real):
1. Cada branch deve ter seu próprio banco PostgreSQL (como data branches)
2. Merge deve aplicar SQL apenas no banco da branch de destino
3. Branches nunca devem compartilhar o mesmo banco
4. "main" deve ser apenas uma referência, não um banco compartilhado
